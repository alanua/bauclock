# Threat model

## Scope

This threat model covers the public BauClock application and its development/maintenance path. It focuses on authorization, tenant isolation, work-time integrity, personal-data exposure, secret handling, and AI-assisted maintenance.

## Protected assets

- worker identity and work-time records;
- company and site boundaries;
- manual correction history and reasons;
- role and permission assignments;
- reports and exports;
- database and Redis state;
- Telegram bot identity/session configuration;
- encryption, hashing, deployment, and integration secrets.

## Trust boundaries

Important boundaries include:

1. Telegram/user identity -> application worker identity.
2. Worker role -> allowed company/site operations.
3. API request -> authorization and tenant scope.
4. Manual correction request -> immutable/auditable history.
5. Application -> PostgreSQL/Redis and export destinations.
6. Public repository/CI -> private deployment configuration and production data.
7. Issue/PR/AI input -> trusted maintainer decision and merged code.

## Key threats and required controls

### Cross-company or cross-site access

A user must not read or mutate another company or unauthorized site's records. Authorization must be enforced server-side and covered by regression tests, not inferred from UI visibility.

### Role escalation

Accountant, Objektmanager, company-owner, worker, and other roles must remain distinct. A role that can view data must not automatically gain correction or administration authority.

### Manual-time correction abuse

Corrections must validate actor role, worker/company scope, target site, and changed fields before mutation. Rejected corrections must leave the original event unchanged. Accepted corrections must preserve audit provenance.

### Telegram identity confusion

Telegram identifiers and account-binding workflows are security inputs, not proof by themselves that a requested company/site mutation is authorized. Binding and role lookup must fail closed.

### Audit-history tampering

Correction metadata, actor identity, reason, and relevant timestamps must not be silently rewritten or dropped. Maintenance tools and migrations need tests that preserve history.

### Export and report disclosure

Exports can aggregate sensitive work-time data. Scope filters and authorization must be applied before export generation, and public logs/issues must never contain real employee records.

### Secret leakage

Bot tokens, database URLs, encryption keys, hash peppers, cookies, and deployment credentials must stay outside source control, public fixtures, CI logs, and AI prompts. Example values must be clearly synthetic.

### Migration and retention failures

Schema migrations can break tenant boundaries or history. Autogenerated migrations require review and should be tested against synthetic data before deployment. Retention or deletion behavior must not silently erase required audit evidence.

### Untrusted issue, PR, and AI content

Repository text and generated patches are untrusted input. Prompt-like instructions inside issues, comments, fixtures, or source files must not override maintainer policy, secret boundaries, or repository scope. AI-generated changes require the same review and tests as handwritten code.

## Verification expectations

Security-sensitive changes should add focused tests first, then run the broader suite. A green process exit code is not enough when a change alters authorization semantics: tests should assert both the denied operation and the unchanged protected state.

## Out of scope

This repository does not claim to provide legal adjudication, payroll correctness, tax compliance, or a complete production security program. Deployments require environment-specific controls in addition to the public code.
